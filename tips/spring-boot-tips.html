Spring Boot 실전 팁 모음 — 운영에서 살아남는 설정들

#spring-boot#java#backend#tips#production

1. 헬스체크 설정 제대로 하기

쿠버네티스에서 /actuator/health 만 쓰면 안 됩니다.

# application.yml
management:
  endpoint:
    health:
      probes:
        enabled: true  # liveness, readiness 분리
      show-details: when-authorized
  endpoints:
    web:
      exposure:
        include: health, info, metrics, prometheus
# k8s deployment.yml
livenessProbe:
  httpGet:
    path: /actuator/health/liveness   # JVM 살아있나?
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10
 
readinessProbe:
  httpGet:
    path: /actuator/health/readiness  # 트래픽 받을 준비됐나?
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5

Liveness vs Readiness 차이:

  • Liveness: 앱이 살아있나? (죽으면 재시작)
  • Readiness: 트래픽을 받을 준비가 됐나? (NO면 LB에서 제외)

DB 연결이 끊어져도 JVM은 살아있으므로 Liveness는 통과, Readiness는 실패해야 합니다.

2. @Transactional 함정들

// ❌ 함정 1: self-invocation - 트랜잭션 적용 안 됨
@Service
public class OrderService {
 
    public void process(Long orderId) {
        this.processInternal(orderId);  // self-call → AOP 프록시 우회!
    }
 
    @Transactional
    public void processInternal(Long orderId) {
        // 트랜잭션이 시작되지 않음!
    }
}
 
// ✅ 해결: ApplicationContext에서 빈 주입, 또는 분리
@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderInternalService internalService;
 
    public void process(Long orderId) {
        internalService.processInternal(orderId);  // 다른 빈 → AOP 작동
    }
}
// ❌ 함정 2: 예외를 잡으면 롤백 안 됨
@Transactional
public void cancelOrder(Long orderId) {
    try {
        order.cancel();
    } catch (Exception e) {
        log.error("취소 실패", e);  // 예외를 삼켜버리면 롤백 안됨!
    }
}
 
// ✅ 해결: 명시적 롤백 마킹
@Transactional
public void cancelOrder(Long orderId) {
    try {
        order.cancel();
    } catch (Exception e) {
        TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
        log.error("취소 실패", e);
    }
}

3. Connection Pool 튜닝

spring:
  datasource:
    hikari:
      # 공식: pool size = (core_count * 2) + effective_spindle_count
      # 4코어 SSD 기준: 4 * 2 + 1 = 9 → 10으로 반올림
      maximum-pool-size: 10
      minimum-idle: 5
      connection-timeout: 3000   # 3초 이상 기다리지 말 것
      idle-timeout: 600000       # 10분 유휴 후 반납
      max-lifetime: 1800000      # 30분 후 커넥션 교체 (DB 타임아웃 대비)
      
      # 커넥션 유효성 검사
      keepalive-time: 30000      # 30초마다 ping
      connection-test-query: SELECT 1

Pool size를 크게 하면 빨라질까? 아닙니다. Pool이 크면 DB 서버에 동시 쿼리가 많아져 DB가 오히려 느려집니다. HikariCP 공식 문서는 “think small” 를 강조합니다.

4. Caffeine 로컬 캐시 활용

Redis 없이 빠른 응답을 위한 로컬 캐시:

@Configuration
@EnableCaching
public class CacheConfig {
 
    @Bean
    public CacheManager cacheManager() {
        CaffeineCacheManager manager = new CaffeineCacheManager();
        manager.setCaffeineSpec(CaffeineSpec.parse(
            "maximumSize=10000,expireAfterWrite=5m"
        ));
        return manager;
    }
}
 
@Service
public class ProductService {
 
    @Cacheable(value = "products", key = "#productId")
    public Product findById(Long productId) {
        return productRepository.findById(productId)
            .orElseThrow(() -> new ProductNotFoundException(productId));
    }
 
    @CacheEvict(value = "products", key = "#product.id")
    public void update(Product product) {
        productRepository.save(product);
    }
}

5. MDC로 분산 추적 로깅

마이크로서비스 환경에서 요청 추적:

// Filter에서 Trace ID 설정
@Component
public class TraceIdFilter extends OncePerRequestFilter {
 
    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) throws IOException, ServletException {
        String traceId = Optional.ofNullable(request.getHeader("X-Trace-Id"))
            .orElse(UUID.randomUUID().toString().replace("-", "").substring(0, 16));
 
        MDC.put("traceId", traceId);
        MDC.put("userId", getUserId(request));  // 인증된 사용자 ID
 
        try {
            response.setHeader("X-Trace-Id", traceId);  // 응답 헤더에도
            chain.doFilter(request, response);
        } finally {
            MDC.clear();  // 필수! 스레드 재사용 시 오염 방지
        }
    }
}
<!-- logback-spring.xml -->
<pattern>%d{HH:mm:ss} [%X{traceId}] [%X{userId}] %-5level %logger{36} - %msg%n</pattern>

로그 예시:

14:32:01 [a3f9b2c1] [user:12345] INFO  OrderService - 주문 생성 시작: ORD-001
14:32:01 [a3f9b2c1] [user:12345] INFO  PaymentService - 결제 요청: 159,000원
14:32:02 [a3f9b2c1] [user:12345] INFO  OrderService - 주문 완료: ORD-001

모든 로그에 동일한 traceId가 찍혀 요청 흐름 전체를 추적할 수 있습니다.

RESTful API 설계 원칙 — 실무에서 배운 것들

#api#rest#design#backend

API 설계는 처음엔 쉬워 보이지만, 프로덕션에서 수백만 요청을 처리하다 보면 초기 설계의 실수가 뼈아프게 돌아옵니다.

1. URL 설계: 명사를 쓰고, 동사를 피하라

❌ 잘못된 예 (동사 사용):

GET  /getOrders
POST /createOrder
PUT  /updateOrderStatus

✅ 올바른 예 (명사 + HTTP 메서드):

GET    /orders           # 목록 조회
POST   /orders           # 생성
GET    /orders/{id}      # 단건 조회
PUT    /orders/{id}      # 전체 수정
PATCH  /orders/{id}      # 부분 수정
DELETE /orders/{id}      # 삭제

2. 버전 관리 — URL vs 헤더

URL 방식

GET /api/v1/orders
GET /api/v2/orders
  • 명시적이고 이해하기 쉬움
  • 브라우저 캐시 친화적
  • URL이 길어짐

헤더 방식

GET /api/orders
Accept: application/vnd.nike.v2+json
  • URL이 깔끔
  • 클라이언트 구현이 복잡
  • 헤더를 깜빡하면 디버깅 어려움

추천

결론: URI 버전 관리를 추천합니다.

나이키 코리아 프로젝트에서 헤더 방식을 먼저 시도했다가 클라이언트 팀(iOS/Android/Web) 모두에서 불만이 나왔습니다. URL이 좀 더 길어도 명시적인 게 낫습니다.

3. 응답 구조 표준화

팀 전체가 동일한 응답 구조를 써야 프론트엔드와 협업이 편합니다.

// 표준 응답 래퍼
public record ApiResponse<T>(
    boolean success,
    T data,
    ErrorInfo error,
    PageInfo page  // 페이지네이션 시 사용
) {
    public static <T> ApiResponse<T> ok(T data) {
        return new ApiResponse<>(true, data, null, null);
    }
 
    public static <T> ApiResponse<T> paged(T data, PageInfo page) {
        return new ApiResponse<>(true, data, null, page);
    }
 
    public static <T> ApiResponse<T> error(ErrorInfo error) {
        return new ApiResponse<>(false, null, error, null);
    }
}
// 성공 응답
{
  "success": true,
  "data": {
    "orderId": "ORD-2026-001",
    "status": "CONFIRMED",
    "totalAmount": 159000
  }
}
 
// 에러 응답
{
  "success": false,
  "error": {
    "code": "ORDER_001",
    "message": "재고가 부족합니다.",
    "details": { "productId": "NK-AIR-MAX-001", "requested": 3, "available": 1 }
  }
}

4. HTTP 상태 코드 올바르게 사용하기

가장 흔한 실수: 모든 응답을 200 OK로 내리고 body에 에러를 담는 것. HTTP 상태 코드는 표준이고, 로드 밸런서/모니터링 도구 모두 이를 기반으로 동작합니다.

상황올바른 코드잘못된 코드
생성 성공201 Created200 OK
조회 성공200 OK-
비동기 처리 시작202 Accepted200 OK
No body 응답204 No Content200 OK
잘못된 요청400 Bad Request200 OK
인증 필요401 Unauthorized403 Forbidden
권한 없음403 Forbidden401 Unauthorized
리소스 없음404 Not Found200 OK + null
서버 에러500 Internal Server Error200 OK

5. 페이지네이션 설계

// Cursor 기반 페이지네이션 (대용량 데이터에 추천)
@GetMapping("/orders")
public ApiResponse<List<Order>> getOrders(
    @RequestParam(required = false) String cursor,
    @RequestParam(defaultValue = "20") int limit
) {
    List<Order> orders = orderService.findByCursor(cursor, limit + 1);
    boolean hasNext = orders.size() > limit;
 
    return ApiResponse.paged(
        orders.subList(0, Math.min(limit, orders.size())),
        PageInfo.of(hasNext, hasNext ? orders.get(limit).getId() : null)
    );
}

Offset 페이지네이션 vs Cursor 페이지네이션

  • Offset: 구현 쉬움, 하지만 대용량에서 느림 (LIMIT 10 OFFSET 100000은 처음 100010개 읽음)
  • Cursor: 구현 복잡, 하지만 일관된 성능 보장

주문 내역, 피드처럼 실시간으로 데이터가 추가되는 목록엔 Cursor 방식이 적합합니다.
